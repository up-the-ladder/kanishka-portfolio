Multimodal Video Search & Ranking Engine

Natural-language search inside video · In development

Python · PyTorch · Whisper · OpenCLIP · BLIP · FAISS · BM25 · cross-encoders · FastAPI · Redis · PostgreSQL · Docker

At a glance

  • Answers queries like “the part where they explain the loss function” by returning the video segment, not the video.
  • Each segment is indexed four ways: spoken transcript, visual frame content, on-screen text, and a generated caption.
  • Retrieval is two-stage: sparse BM25 and dense FAISS candidates, fused, then optionally reranked by a cross-encoder.
  • Every stage is defended by an ablation: transcript-only, visual, sparse, dense, hybrid, and reranked systems are compared on the same queries.
  • Evaluation uses Recall@K, MRR, NDCG, and latency, so quality gains are weighed against what they cost.

Problem

Video search usually operates on titles, descriptions, and tags, which is metadata written by a human about a whole file. What people actually want is the moment: a specific segment where something is said, shown, or written on screen. That requires searching the content itself, and the content is not one signal but several, each of which fails in different ways.

Motivation

Transcripts alone miss anything demonstrated rather than narrated. Frame embeddings alone miss precise terminology. On-screen text carries slide titles, code, and labels that nobody says out loud. Combining them is the obvious move, which is exactly why it needs to be measured rather than assumed. More modalities means more index cost and more latency, and the payoff has to be real.

Indexing pipeline

Videos are segmented, and each segment is represented across four modalities:

  • Spoken transcript. Whisper, giving searchable text aligned to time.
  • Visual frames. OpenCLIP embeddings, giving a shared space for text queries and images.
  • On-screen text. OCR, recovering slide, caption, and interface text.
  • Generated captions. BLIP, describing what a frame shows when nobody says it.

The output is a segment-level index where a single moment is reachable through whichever signal happens to carry the answer.

Retrieval and ranking

Query → sparse (BM25) and dense (FAISS) candidate retrieval → multimodal fusion → optional cross-encoder reranking → ranked segments.

The first stage is cheap and recall-oriented: BM25 handles exact terms, names, and jargon, while FAISS handles paraphrase and semantic overlap. Their candidates are fused across modalities. The second stage is expensive and precision-oriented: a cross-encoder scores query and segment together and reorders the shortlist. Splitting the two is what keeps the system serviceable, because the model that is good enough to rank well is far too slow to run over the whole corpus.

How the architecture is justified

The project treats “add another model” as a claim that has to be tested. Six system variants (transcript-only, visual, sparse, dense, hybrid, and reranked) are compared under a controlled retrieval evaluation, so each component earns its place by improving results on the same queries rather than by being present in the diagram.

Metrics are Recall@K (did the right segment survive the first stage), MRR and NDCG (is it near the top after ranking), and latency (what the quality cost). Reranking in particular only makes sense if the NDCG it buys is worth the milliseconds it spends, which is why latency is measured alongside quality rather than reported separately.

Engineering decisions

Segment-level indexing rather than video-level. The unit of retrieval should be the unit the user wants. Indexing whole videos makes the ranking problem easier and the product worse.

Sparse and dense together rather than choosing one. They fail on opposite query types. Keeping both, and fusing, avoids optimizing for whichever query set was tested first.

Cross-encoder reranking as an optional stage. Making it toggleable is what makes the ablation possible and keeps a cheaper configuration available.

Latency treated as a first-class metric. A retrieval system that is only evaluated on NDCG will happily become unusable.

Tradeoffs

  • Four modalities give better coverage but multiply indexing cost and storage per hour of video.
  • Cross-encoder reranking improves precision but adds per-query latency, which is why it stays optional.
  • Fine-grained segments improve precision but enlarge the index and can fragment context that spans a boundary.
  • Generated captions add signal but introduce model-authored text into the index, which can mislead as well as help.

What’s next

  • Publish the ablation table so the component-by-component gains are visible rather than described.
  • Report latency per stage, not just end to end.
  • Error analysis on the queries the hybrid system still loses.
